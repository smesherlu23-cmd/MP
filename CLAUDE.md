# CLAUDE.md

Указания для Claude Code при работе с этим репозиторием. Полное техническое
задание — в `SPEC.md`; при расхождении между этим файлом и `SPEC.md` прав
`SPEC.md`.

## Что это

Настольный инструмент ГМ: моделирует боестолкновение двух **отрядов любого
масштаба** — от отделения до полка — и выдаёт человекопонятный исход: потери,
остаточную боеспособность, организацию, снабжение и пошаговый журнал с
объяснением, почему цифры изменились.

## Команды

```bash
python -m pytest                      # все тесты (из корня репозитория)
python -m pytest -m "not slow"        # без длительных статистических тестов
python -m ruff check .                # линтер, должен быть чист
cd wargame_sim && python app.py       # десктопное приложение (Flet)
cd wargame_sim && python cli.py --demo --seed 42          # один бой без UI
cd wargame_sim && python cli.py --demo --runs 200         # массовый прогон
cd wargame_sim && python cli.py --demo --runs 200 --symmetric   # проверка баланса
cd wargame_sim && python cli.py --demo --small --seed 42  # взвод против взвода
```

`cli.py` — рабочий инструмент калибровки: любое изменение коэффициентов надо
проверять им до того, как оно попадёт в конфиг.

## Жёсткие правила

1. **Ни одного числового коэффициента в коде.** Все числа живут в
   `wargame_sim/config/*.yaml`. Если формуле нужна новая зависимость — заводится
   новая кривая или поле в конфиге, а не литерал в Python. Проверяется глазами
   при ревью и косвенно тестом `tests/test_architecture.py`.
2. **`core/` не импортирует `flet`.** Проверяется тестом.
3. **`ui/` не содержит формул** — только вызовы `core` и отрисовка. Тест ищет
   в `ui/` арифметику с числовыми литералами; если понадобилась «настоящая»
   величина (например, предел сида), её место в `core`.
4. **Детерминизм по сиду.** Глобальный `random` не используется; каждый бросок
   берётся из `RngStreams`, ключ потока обязан включать сторону
   (`A/rota_1`, не `rota_1`) — иначе стороны делят поток и появляется перекос.
   Свёртка ключа — `blake2b`, а не встроенный `hash()`: тот рандомизируется
   между процессами и ломает `multiprocessing`.
5. **Учёт потерь через реестр.** `personnel_lost` + `personnel_current` всегда
   равно исходной численности; новые источники потерь обязаны идти через
   `apply_personnel_loss` / `apply_vehicle_loss`.

## Оформление

Единственный источник правды — `ui/theme.py`: ни одного цвета и размера
«россыпью» по экранам. Цветом обозначаются только потери (`LOSS`), подавление
(`WARN`) и «бой идёт» (`OK`); стороны A и B различаются буквой и положением,
а не цветом.

### Две темы

Цвета живут в `Palette` — два экземпляра, `LIGHT` и `DARK`. `theme.apply(dark)`
раскладывает выбранную палитру по константам модуля, поэтому экраны
по-прежнему пишут `t.CARD_BG` и про тему не знают; после переключения
достаточно перестроить содержимое (`ui/app.py: paint()` + `render()`).

Тёмная — та же бумага при свете лампы, а не чёрный терминал: тот же тёплый
тон и **тот же порядок слоёв** (карточка светлее содержимого, содержимое
светлее полотна), поэтому вёрстка читается одинаково в обеих темах. Акценты
подняты по светлоте: кирпичный `#A83E28` на тёмном не читается, а разница
«потери / подавление» обязана оставаться видимой.

Три места, где легко сломать:

1. **Аргумент по умолчанию вычисляется один раз при импорте.** `def text(...,
   color=TEXT)` заморозил бы светлую тему навсегда, поэтому у всех функций
   оформления по умолчанию `None`, а цвет подставляется в теле (`color or TEXT`).
   Тест `test_default_arguments_do_not_freeze_the_light_palette` это стережёт.
2. **Часть интерфейса красит Flutter, а не наша вёрстка**: выпадающее меню
   списка, подсказка, снек-бар, полоса прокрутки. Их накрывает `theme.flet_theme()`,
   и `page.theme` с `page.dark_theme` задаются **обе** — `theme_mode` только
   выбирает, какую взять. Меню `ft.Dropdown` вдобавок красится своим
   `menu_style`: без него в тёмной теме оно раскрывалось белым.
3. **Графики рисует matplotlib** (`ui/charts.py`) — он берёт цвета в момент
   вызова, поэтому следует за палитрой сам; тест сверяет, что два PNG разные.

Выбранная тема запоминается в `data/ui.json` (`AppState._settings`): битый или
отсутствующий файл — это светлая тема, а не падение.

Тест `test_every_screen_uses_only_palette_colors` проверяет каждый экран в обеих
темах на то, что **все** назначенные цвета принадлежат действующей палитре.
Он же ловит цвет, вписанный в экран руками, — так нашёлся `#DDD7CC` в плашке
активного подпункта навигации.

### Действия живут на строке

Правило простое: **что делают со строкой — делают на строке**. Наведение
подсвечивает её (`t.ROW_HOVER`), курсор становится «рукой» там, где щелчок
что-то меняет, правая кнопка открывает меню действий над этой самой
строкой. Всё это — одна функция `common.interactive(row, on_click=, menu=)`,
через неё пропускают строку `common.table_row` и `library.folder_header`,
поэтому меню появляется везде, где есть список: папки и записи мат.части,
типы солдат, отряды, группы в конструкторе и в дереве боя, бои и сценарии
в архиве. Меню собирается из `common.MenuItem(label, action, icon=, danger=)`.

Необратимое спрашивает. `ui/widgets/dialogs.py` даёт четыре окна в токенах
приложения: `confirm` (удаление), `ask_name` (имя папки), `pick` (куда
положить) и `split_group` (деление с долями и предпросмотром). Приёма «нажмите
ещё раз, чтобы подтвердить» в интерфейсе больше нет — он был из терминала.

Предпросмотр деления считает та же `core.formation.apportion`, которой потом
делит движок: показанные числа — это ровно то, что произойдёт, а не оценка.

### Интерфейс не выдумывает

Три места, где он раньше врал, и правило по каждому:

1. **Кнопка без действия — не кнопка.** «Копировать» и «Экспорт» в
   конструкторе отряда были `lambda: None`, а семь разных плашек шаблонов
   делали одно и то же (открывали первый отряд). Либо действие настоящее,
   либо кнопки нет.
2. **Итог — только по законченному бою.** `engine.result()` подставляет
   «ничья по лимиту ходов», если бой не кончился, поэтому кнопка «Итог»
   проверяет `engine.finished` и предлагает довести бой до конца.
   `AppState.ensure_battle()` по той же причине сверяет отпечаток сценария:
   правка сида или подразделения начинает бой заново, а не выдаёт старый
   движок за новый.
3. **Битый файл виден.** `storage.scan_*` возвращает и прочитанное, и причину
   по каждому непрочитанному файлу; экраны показывают предупреждение. Раньше
   подразделение просто пропадало из списка.

### Перерисовывается изменившееся

Журнал за бой набирает около 2600 записей, и полная сборка трёхсот плиток
стоит 85 мс — при смене приказа это ровно 300 лишних плиток на одну новую
запись. `journal.EntriesView` помнит показанное окно и, если список только
вырос с конца, строит **только новые** плитки: команда обходится в 0.3 мс,
целый ход — в 36 мс вместо 85. Полная пересборка остаётся на смену фильтра
и детальности. Показываются при этом **последние** записи, а не первые:
обрезка с начала оставляла ГМ первые два хода.

Рамка (навигация слева + верхняя полоса) живёт в `ui/shell.py` и одинакова на
всех экранах: переход подсвечивает пункт и перерисовывает только контент,
поэтому кнопок «назад» и «на главную» нет. Анимаций нет намеренно: кнопки
не переливаются, а переход не анимируется, потому что приложение держит
**один-единственный `ft.View`** и меняет его содержимое. Если снова начать
класть новый View в `page.views`, Flutter вернёт анимацию навигации.

Шрифты лежат в `assets/fonts` и грузятся с диска — приложение не ходит в сеть.
Одно семейство во Flet — один файл, поэтому 500 и 600 зарегистрированы
отдельными семействами (`IBM Plex Sans Medium`, `… SemiBold`): если вместо
этого попросить `weight=W_600` у обычного начертания, Flutter подделает
жирность и текст поплывёт. Выбор семейства по весу делает `theme._family`,
тест `test_screens_use_only_registered_fonts` ловит незарегистрированное.

Редактор коэффициентов не свёрстан по картинке: поля строятся
`core.config.introspect.describe()` по реальной схеме и реальному YAML, а
границы полей — по ограничениям pydantic. Новый коэффициент в конфиге
появляется в интерфейсе сам. Правка пишется точечно в текст файла
(`patch_scalar`), поэтому комментарии в конфиге остаются на месте; настоящая
проверка — всё равно pydantic при сохранении. Конструктор техники правит
`vehicles.yaml` тем же способом, а создаёт и удаляет машины через
`append_entry`/`remove_entry` — блоками, тоже не трогая пояснения.

## Мат.часть и штат

Четыре библиотеки, устроенные одинаково: папки (`folders`, в том числе
пустые) плюс записи с полем `folder`.

Папка — путь через «/»: `Бронетехника/Танки`. Операции над папками живут в
`core/config/folders.py` (создать, переименовать, перенести, удалить) и
правят YAML точечно, поэтому пояснения в конфигах переживают любую из них;
удаление поднимает содержимое на уровень выше, ничего не теряя. В
интерфейсе папка выбирается щелчком по её строке, и справа открывается
карточка папки вместо карточки записи — имя, родитель, удаление
(`ui/widgets/library.py`).

Часть полей библиотек пока только хранится и правится, но в расчёт не идёт;
такие подписаны «· справочно» прямо в карточке. Сейчас это дальность и
расчёт оружия, заметность и подвижность комплекта, подвижность и
вместимость машины, БК солдата. Появится механика — снимем пометку.

- `vehicles.yaml` — машины, двенадцать полей на карточку;
- `weapons.yaml` — пехотное вооружение: расчёт, огневая мощь,
  противотанковая мощь, дальность, расход боезапаса;
- `gear.yaml` — обмундирование: защищённость, заметность, подвижность,
  множитель усталости;
- `troops.yaml` — типы солдат: кому какое обмундирование, оружие,
  доп. оружие и БК выданы, плюс раздел `staff` с правилами перевода
  комплекта в штат.

Экраны `ui/views/materiel.py` (три библиотеки мат.части одним экраном,
различия в `LIBRARIES`) и `ui/views/troops.py` (сборка юнитов).

**Из комплекта в числа элемента** — `core/staff.py`. Тип элемента может быть
описан составом (`element_types.yaml: composition` — сколько каких солдат).
Тогда численность, огневая мощь и устойчивость считаются по карточкам, а не
задаются руками, и правка в библиотеке сразу видна в новом подразделении.

Роль учитывается отдельно: `staff_attack` и `staff_defense` — какая доля
огневых возможностей и защищённости штата реализуется в бою. Штаб вооружён,
но стрелковой ротой не является, поэтому у него доля огня 0.25.

Доли роли подобраны так, что расчётный штат **точно воспроизводит** прежние
числа всех семи типов (тест `test_composition_reproduces_the_hand_set_numbers`):
переход на состав не сдвинул калибровку ни на единицу. Смысл появился тогда,
когда подразделение перевооружают — тогда числа едут за комплектом.

Техника участвует в расчёте семью полями карточки:

- `anti_tank` — противотанковые возможности элемента берутся как лучшее из
  трёх: пехотные средства типа, состав (`staff`) и пушки машин
  (`formulas.anti_tank_share`);
- `armour_front` / `armour_side` — через кривую `combat.curves.armour`; по
  отступающему и паникующему бьют в борт;
- `crew` — столько л/с уходит с уничтоженной машиной (доля —
  `vehicles.crew_loss_share`);
- `visibility` — множитель веса цели в целеуказании;
- `reliability` — небоевой износ в фазе восстановления;
- `fuel_use` — множитель расхода топлива.

Комплект солдата тоже стоит подразделению: `core.staff.element_load()` даёт
множители усталости (по `gear.fatigue`) и расхода боезапаса (по
`weapon.ammo_use`). Обе величины нормированы базами из `troops.yaml`
(`fatigue_baseline`, `ammo_baseline`), подобранными так, что у стрелковой
роты они равны единице — калибровка не двигается, а тыл с пистолетами тратит
боезапас втрое медленнее.

Кривая брони подобрана так, что БТР даёт множитель 1.00: нынешние
подразделения считаются ровно как раньше, и карточка начинает влиять на
исход только тогда, когда технику действительно меняют.

## Отряд — это дерево групп

Бой не «батальон на батальон». Сторона боя — **отряд**: дерево групп любого
масштаба. Рота делится на взводы, взвод на отделения, техника живёт отдельной
группой. Глубина не ограничена.

**Дерутся листья дерева.** Группа с подгруппами сама огня не ведёт — она
показывает их сумму (`Battalion.rollup`). Благодаря этому движок по-прежнему
видит плоскую линейку (`alive_elements` = введённые в бой живые листья), и ни
одна фаза про дерево не знает: калибровка от перестроения не поехала.

- `Element.parent` — id старшей группы, `Element.echelon` — ступень (звено,
  отделение, взвод, рота, батальон, полк). Подгруппа получает ступень **ниже**
  автоматически (`echelon_below`), поэтому дерево читается без подписей руками.
- `Battalion.scale` — масштаб отряда целиком. Он не украшение: от него зависит
  задача приказа «оборона» (`orders.scale_turns`) — взвод держит 12 ходов,
  рота 16, батальон 22. У батальона множитель 1.00, поэтому батальонная
  калибровка от этой таблицы не зависит.
- `Element.engaged` — введена ли группа в бой; наряд сил назначается
  **листьями**, а щелчок по старшей группе доходит до всех её подгрупп
  (`formation.set_engaged`).
- Дерево проверяется моделью: несуществующий родитель и кольцо подчинения
  дают понятную ошибку, а не бесконечный обход.

### Перестроение — `core/formation.py`

Чистые операции над моделью; перенос реестра потерь и журнал — на движке.

- `split(battalion, id, parts, shares=…)` — разделить лист на подгруппы;
- `detach_vehicles(battalion, id, config)` — вывести технику отдельной
  группой вместе с экипажами (`crew` из карточки машины); пехота остаётся
  спешенной — это и есть цена того, что звено ушло действовать отдельно;
- `merge(battalion, id)` — свести подгруппы обратно: количества
  складываются, «плотности» (мораль, боезапас, выучка) усредняются по числу
  людей в строю;
- `reassign` / `set_engaged` — переподчинить ветку и назначить наряд сил.

Главное правило — **сумма сходится**. Раскладка целых идёт методом
наибольших остатков (`apportion`), а `fit_under` возвращает излишек туда, где
есть запас, чтобы «в строю» ни у одной подгруппы не превысило её штат.

### Перестроение прямо в бою

`BattleEngine.split / detach_vehicles / merge` работают на любом ходу и
переносят учёт: подгруппа получает свою долю уже понесённых потерь, и
равенство «потеряно + в строю = на начало» держится и после деления (§4.2).
Обе команды, как `commit` и `set_order`, пишутся в журнал фазой `command` —
по нему видно, какие решения принимал ГМ и на каком ходу.

Побочное следствие деления честное и полезное: у трёх взводов бросок потерь
шире, чем у одной роты (биномиальный разброс зависит от размера цели), а
организация считается по числу живых листьев. Дробить силы рискованно — как
и должно быть.

### Снабжение малой группы

`supply.external_supply_share` — доля обычного подвоза отряду, у которого
тыла **нет по штату**: взвод и отделение снабжает старшая часть. Это не то
же самое, что выбитый тыл: там подвоз обрывается совсем, и это интересное
событие боя. Без этой развилки взвод приходил к пятому ходу с нулевым
боезапасом, и модель переставала различать исходы.

### Интерфейс

Пульт боя — карточка «Боевой порядок»: дерево со сдвигом по уровням,
раскрытие «галочкой», щелчок выбирает группу. Действия над выбранной живут
в **подвале** карточки и зависят от того, что выбрано: у листа — приказ,
деление на 2/3/4, отделение техники; у старшей группы — «Свести»; у резерва —
«Ввести в бой». Виджет дерева общий (`ui/widgets/orbat.py`), его же
использует наряд сил на экране подготовки и конструктор отряда.

## Движок

Ход — строгая последовательность из `PHASE_ORDER`. Фазы выбора целей,
воздействия, потерь и подавления выполняются **по сторонам в порядке
инициативы**, поэтому бонус первого удара действительно означает удар первым.

Фаза восстановления на первом ходу не работает: бой ещё не начинался, и
бесплатный тик подвоза, отдыха и готовности до первого выстрела — артефакт,
а не механика.

### Мораль

`Δмораль = k7 × успех − давление / устойчивость`, где устойчивость —
приказ × опыт × командир. **Положительных слагаемых «просто так» нет.**
Командир и опыт мораль держат (делителем), а не начисляют; единственный
плюс даёт успех в ходу, и его надо заработать. Вес `k7_side_success`
большой (190) намеренно: на входе разница долей потерь порядка 0.01…0.03,
и при прежних 3.5 победитель не получал за победу ничего — обе стороны
сползали к нулю одинаково.

Восстановление морали работает **только вне контакта** — то же условие,
что у отдыха от усталости. Под огнём не рассыпаются, но и не приходят
в себя.

### Слаженность и готовность

Обе были константами весь бой; теперь обе живые.

- **Слаженность** рвут потери и подавление (`combat.cohesion`), собирает
  обратно только время вне контакта. Входит в K_сост, в разброс огня и
  в инициативу, поэтому обескровленный отряд и стреляет хуже, и теряет
  инициативу.
- **Готовность** тратится на команды: смена приказа, деление, сведение,
  ввод резерва (`combat.readiness`). Перестроение посреди боя перестало
  быть бесплатным. Автоматическая смена приказа при панике и отходе стоит
  столько же, сколько команда ГМ, — это тоже потеря управления.

  В массовом прогоне без команд готовность почти не двигается, и это
  правильно: она отвечает на решения, а не на ход времени. Проверяется
  поэтому не статистикой, а прямым тестом
  `test_readiness_is_spent_by_commands`.

### Контакт

В контакте тот, **кого видит противник**. Раньше признак ставился всей
стороне, стоило ей увидеть хоть кого-нибудь: отдыхать не мог никто, тыл и
резерв считались под огнём, а усталость упиралась в потолок и переставала
различать подразделения.

### Исход

Выполненная задача снимает «поражение по выходу из боя». Засада и отход
тем и заканчиваются, что сторона уходит; считать это поражением — значит
объявлять проигравшим того, кто сделал ровно то, что ему приказали.
Разгром и паника задачей не отменяются.

### Случайность

Случайность живёт внутри механики, а не в таблице происшествий:

- потери бросаются, а не вычисляются — `rng.binomial` даёт число успехов
  через обратную функцию распределения. Матожидание равно прежней формуле,
  поэтому калибровка не едет, а разброс сам собой зависит от размера цели:
  у взвода он втрое шире, чем у роты. Один бросок потока на вызов — расход
  потока не зависит от численности, и бой остаётся воспроизводимым;
- кривая `combat.curves.collapse` растёт монотонно и полого: концентрация
  огня выгодна, но скачка нет. Скачок был — и модель балансировала на его
  колене;
- ширину случайного множителя огня задаёт выучка (`formulas.noise_range`):
  произведение трёх кривых по опыту, эффективной слаженности и подавлению.
  Центр диапазона не двигается, поэтому средний огонь прежний.

Каждая фаза пишет в журнал. Для потерь, морали и подавления поле `breakdown`
обязательно: по нему ГМ видит, какие модификаторы сработали и с какими числами.
Подробный журнал — около 1000 записей на бой; для массовых прогонов движок
создаётся с `verbose=False`, это меняет только объём журнала, но не расчёт
(проверяется тестом).

## Калибровка

Текущие значения подобраны прогонами `cli.py` и держат:

- **исход решает бой, а не счётчик.** Это главный показатель: доля боёв,
  которые закончил не противник, а выполнение задачи обороны или предел
  ходов. Сейчас 4% (114 из 120 боёв кончаются паникой одной из сторон);
  было 75%, и пока было так, всё остальное не имело значения — модель
  была секундомером;
- равные отряды в равных условиях — 50/50 на 200 прогонах;
- «атака» против «обороны» при равных силах выигрывает примерно в 30%
  случаев. Обороняться выгоднее — так и должно быть;
- длительность 17.3 хода при разбросе 14…21, предел 30 не достигается.
  Задача обороны (`hold_turns: 22`) — подстраховка, а не секундомер: она
  длиннее типичного боя и срабатывает в 4% случаев;
- у победителя остаётся 40–55% боеспособности;
- **любой внешний параметр даёт градиент, а не обрыв.** Доля побед атаки
  по местности: 30% на равнине, 22% на холмах, 14% в болоте, 10% в лесу,
  10% в застройке. Погода: 30 / 18 / 13 / 10. Время суток: 30 / 22 / 14.
  Опыт: 5 / 26 / 68 / 95. Ноль и сто процентов — признак поломки, а не
  «очень сложных условий».

  Осторожно с разбросом этих множителей: **любое снижение общей
  летальности играет за обороняющегося**, потому что ему достаточно
  выстоять. Поэтому укрытие местности, точность погоды и ночи держатся
  сдержанными: широкий разброс снова превращает тяжёлые условия в
  автоматическую победу обороны;
- у каждого приказа есть и победы, и поражения. Проверять это надо
  против **наступающего** противника: два пассивных приказа друг против
  друга (закрепление против обороны) по построению дают ничью — оба
  выполняют задачу «выстоять», и победы там не бывает ни у кого;
- малый масштаб держится теми же показателями: взвод против взвода даёт
  20% атаке и 53/45 в симметричном бою, а боезапас там проседает до 48% —
  у взвода нет штатного тыла, и это видно. Проверяется
  `cli.py --demo --small`.

Всё это закреплено тестами-коридорами (`tests/test_corridors.py`), а не
только наблюдением. Коридоры широкие: они ловят обрывы и константы, а не
стерегут точные числа.

Коридоры считаются через `core.batch.run_batch`, то есть в несколько
процессов: последовательным циклом тот же набор шёл полчаса, а тесты,
которые никто не гоняет, ничего не охраняют. Сейчас весь файл — полторы
минуты.

Две ловушки при чтении результатов:

- **удачный отход и упорное закрепление дают ничью, а не победу.** Отход
  от наступающего — ничья, потому что противник одновременно выполняет
  свою задачу и занимает позицию; закрепление против обороны — ничья,
  потому что оба выполняют «выстоять». Это свойство пары приказов, а не
  поломка, и тест проверяет приказ сразу против атаки и против обороны;
- **победа по задаче не означает сильного победителя.** Отряд, который
  выстоял двадцать ходов, может выйти из боя слабее проигравшего. Строка
  исхода это и говорит; `combat_power` смотрите отдельно.

### Чему нельзя давать сломаться снова

Диагностика вскрыла три способа испортить модель, и каждый из них
выглядел в коде безобидно:

1. **Считать один и тот же факт несколько раз.** Местность резала огонь,
   поднимала устойчивость и ещё поглощала потери — три множителя в одну
   сторону давали ×0.21, и на любой местности кроме равнины атака не
   побеждала ни разу за 150 прогонов. Теперь местность входит в обмен один
   раз, через укрытие, и симметрично; перевес обороны делают приказ и
   укрепления. Так же дважды считался опыт: `combat` входит в K_сост и
   умножает разом огонь и устойчивость, поэтому разброс 0.80…1.25
   превращал опыт в переключатель.
2. **Ставить колено кривой туда, где живёт медиана.** Кривая обвала
   ломалась на давлении 1.20 при медианном давлении в бою 1.21: любой
   модификатор перебрасывал модель через обрыв. Кривые обязаны быть
   монотонными и пологими в рабочем диапазоне.
3. **Начислять что-либо безусловно.** Командир и опыт давали морали
   +2.4 за ход просто так, потери снимали 0.7 — и рота под обстрелом
   набирала мораль. Держать мораль можно (делителем), начислять — только
   за успех в ходу.
4. **Снижать общую летальность «для реализма».** Любое такое снижение
   играет за обороняющегося: ему достаточно выстоять. Поэтому укрытие
   местности, точность погоды и ночи держатся сдержанными — широкий
   разброс снова превращает тяжёлые условия в автоматическую победу
   обороны, и получается не «в лесу тяжелее», а «в лесу невозможно».

Меняя `lethality`, веса морали или пороги, **обязательно** прогоняйте
`python -m pytest -m slow`: показатели связаны, и правка одного сдвигает
остальные.

Особенно чувствителен баланс снабжения. Подвоз (`resupply_per_turn`)
намеренно меньше расхода: боезапас медленно тает и к концу долгого боя
начинает сказываться. Если сделать подвоз больше расхода, снабжение снова
станет украшением — именно так и было, боезапас весь бой стоял на 92%.

`combat_power` («остаточная боеспособность») намеренно не включает
подавление: оно спадает за пару ходов, и с ним любой отряд под огнём
выглядел бы небоеспособным. Мгновенная величина — `effective_power`,
подавление показано отдельной строкой.

## Flet 0.86

Версия заметно отличается от старых примеров:

- `page.go()` объявлен устаревшим; навигация — `page.push_route()` (корутина,
  запускается через `page.run_task`);
- `push_route` на **текущий** маршрут события не порождает, поэтому первый экран
  рисуется явным вызовом, а не «переходом» на `/`;
- активным считается **первый** `View` в `page.views`, а не последний; стек
  экранов и кнопка «назад» ведутся приложением вручную (`ui/app.py`);
- обработчики событий вызываются без аргументов — пишите `lambda *_:`;
- у `TextField` поля называются `helper` и `error` (не `helper_text`/`error_text`);
- у `Dropdown` событие называется `on_select`;
- **в строке с переносом (`wrap=True`) ребёнок обязан быть контейнером со своей
  шириной.** `expand=True` там даёт серый прямоугольник вместо содержимого;
  `ft.Column(width=...)` — тоже (поймано живьём на карточке «условия боя»),
  поэтому `common.labeled(width=...)` возвращает `Container`, а `common.flow`
  заворачивает колонку с шириной сам. Обратная сторона: `ft.Container`
  с `alignment` и без ширины растягивается на всю строку — у чипа
  выравнивания нет именно поэтому;
- `ft.Switch` в 0.86 красится `thumb_color`/`track_color` со словарём по
  `ft.ControlState`; старые `active_color`/`active_track_color` дают
  сплошную тёмную пилюлю без кружка;
- у `ft.Text` нет `letter_spacing` — разрядка живёт в `TextStyle`;
- у `ft.Dropdown` иконка — `trailing_icon`, а не `select_icon`.

Экраны — функции `build(app, ...) -> ft.View`, состояние живёт в `ui/state.py`
и ничего не знает про flet. Благодаря этому тесты строят все экраны без
запущенного окна.

## Сборка Windows EXE

`.github/workflows/build-windows.yml` собирает исполняемый файл через
`flet build windows` (не PyInstaller — это официальный инструмент Flet,
он компилирует приложение как нативное Flutter-приложение со встроенным
Python). Срабатывает при пуше в `main`, при пуше тега `v*` (архив
прикладывается к GitHub Release) и вручную из вкладки Actions; на pull
request гоняются только тесты — сборка exe требует Windows-раннер и
занимает 10–15 минут.

Метаданные и зависимости для сборки — в `wargame_sim/pyproject.toml`
(не в корневом): `flet build` читает `pyproject.toml` из каталога
приложения, а не из корня репозитория, и список `[project.dependencies]`
там — это то, что действительно попадёт внутрь exe. Версия `flet` в нём
закреплена жёстко и обязана совпадать с версией `flet-cli` в workflow
(`env.FLET_CLI_VERSION`) — расхождение ломает сборку. Точка входа задана
через `[tool.flet.app] module = "app"`, потому что `flet build` по
умолчанию ищет `main.py`, а у нас `app.py`.

Собранный `flet build windows` требует запуска именно на Windows —
кросс-компиляция Windows-цели с Linux/macOS не поддерживается (упирается
в MSVC). Flutter SDK ставит сам `flet build` при первом запуске
(`~/.flet/cache`, кешируется между прогонами через `actions/cache`).

Job `build-windows` держит `env: PYTHONUTF8: "1"`: без этого сборка
падает по-настоящему (поймано живым прогоном CI) — консоль
`windows-latest` по умолчанию в `cp1252`, а `flet-cli` пишет в лог через
`rich` символы вроде ✅, которых в `cp1252` нет; `UnicodeEncodeError`
прилетает прямо в середине установки Flutter. Если этот шаг когда-нибудь
уберут — сборка снова начнёт падать на первом же эмодзи в выводе.

## Тесты

`tests/` покрывает требования §12 SPEC: детерминизм по сиду, запрет flet в
`core`, баланс потерь на каждом ходу, завершаемость, все приказы/местности/
погоды/время суток, понятные ошибки конфига, отключение любого опционального
параметра и вероятность победы 50% ± 5%. Длительные статистические тесты
помечены `@pytest.mark.slow`.

`test_vehicles.py` проверяет, что карточка машины действительно влияет на
расчёт: перевооружение меняет исход, по сломанному строю бьют в борт,
неизвестный тип техники даёт понятную ошибку. `test_staff.py` — что состав
воспроизводит прежние числа типов элементов и что перевооружение солдат
меняет штат.

`test_folders.py` — дерево папок, переименование со всеми подпапками,
перенос и удаление без потерь. `test_command.py` — резерв не воюет, после
ввода в бой реестр сходится, смена приказа доходит до расчёта, а не только
до журнала.

`test_formation.py` — деление и сведение: раскладка целых никого не теряет,
разделённая группа уходит с огневой линии, техника отделяется с экипажами,
сведение возвращает остатки, кольцо подчинения не собирается, реестр потерь
сходится после перестроения посреди боя, а взвод без штатного тыла
доживает бой со снабжением.

`test_corridors.py` — коридоры осмысленности боя. Прежние тесты проверяли,
что бой «не упал»: `assert result.turns <= max_turns` проходил и при 0%
побед атаки, и при 100%, поэтому мимо прошло всё сразу. Здесь проверяется
результат: мораль падает под огнём и не восстанавливается в контакте,
слаженность рвётся, готовность тратится на команды, боезапас убывает,
в контакте не весь отряд разом — и статистические коридоры по местностям,
погодам, времени суток, приказам и опыту. Коридоры широкие: их задача —
ловить обрывы и константы («0% всегда», «ровно 16 ходов»), а не стеречь
точные числа. Статистическая часть помечена `@pytest.mark.slow`.

`test_ui.py` строит все экраны без запущенного окна и проверяет не
только «собралось», а и свойства редизайна: обе темы (каждый экран красится
только цветами действующей палитры, цвет по умолчанию не застывает светлым,
графики следуют за темой, выбор темы переживает перезапуск), рамка одинакова везде, активный
пункт навигации ровно один, шрифты только зарегистрированные, пульт боя не
прокручивается, редактор коэффициентов показывает все значения раздела и
видит отличия от эталона. Выключенный тумблер обязан убирать параметр
отовсюду — включая сводку батальона, а не только поля элемента.

Он же стережёт взаимодействие и честность: у строки папки и записи есть
меню правой кнопки, удаление папки сначала спрашивает, предпросмотр деления
показывает ту же раскладку, что и `formation.apportion`, выбранные доли
доходят до деления, «Итог» на незакончившемся бою не собирает результат,
правка сценария начинает бой заново, плашка шаблона действительно добавляет
группу, нечитаемый файл подразделения виден на экране, а журнал показывает
последние записи и дописывает новые вместо полной пересборки.
