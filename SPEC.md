# ТЗ: модульный симулятор боя для варгейма

Документ — спецификация для Claude Code. Кладётся в корень репозитория как `SPEC.md`, рядом с `CLAUDE.md`.

---

## 1. Назначение и границы

Настольный инструмент ГМ: моделирует боестолкновение двух батальонов и выдаёт человекопонятный исход — потери в л/с и технике, остаточную боеспособность, организацию, снабжение и пошаговый журнал с объяснением, почему цифры изменились.

**В объёме:**
- редактор подразделений (конструктор из элементов);
- настройка условий боя;
- пошаговый расчёт с журналом;
- итоговый отчёт;
- массовое моделирование (N прогонов) со статистикой;
- редактирование всех коэффициентов из интерфейса.

**Вне объёма:** сетевая игра, карта и перемещение по местности, экономика/кампания, ИИ-оппонент, более двух сторон.

---

## 2. Стек и жёсткие ограничения

- Python 3.11+, Flet (десктоп), pydantic v2, PyYAML, pytest, ruff.
- Графики: matplotlib → PNG, показывается через `ft.Image`.
- Никаких внешних сервисов и сети. Всё работает офлайн.
- **`core/` не импортирует `flet`.** Проверяется тестом.
- **`ui/` не содержит формул.** Только вызовы core и отрисовка.
- Ни одного числового коэффициента в коде — только в YAML-конфиге. Хардкод чисел в расчётах — ошибка приёмки.

## 4. Модель данных

### 4.1 Элемент подразделения (`Element`)

Батальон состоит из элементов: стрелковые роты, штаб, миномётная батарея, разведвзвод, бронегруппа, тыл/снабжение, инженерный взвод. Тип элемента задаёт его роль в расчёте (см. `config/element_types.yaml`).

| Поле | Тип | Диапазон | Смысл |
|---|---|---|---|
| `id`, `name` | str | — | идентификатор и название |
| `type` | enum | см. конфиг | тип элемента |
| `personnel_full` | int | ≥0 | штатная численность |
| `personnel_current` | int | 0..full | текущая численность |
| `vehicles` | list | — | список `VehicleGroup` |
| `attack` | float | 0..100 | базовая огневая мощь |
| `defense` | float | 0..100 | базовая устойчивость |
| `experience` | int | 1..4 | уровень опыта |
| `morale` | float | 0..100 | моральное состояние |
| `cohesion` | float | 0..100 | связь/слаженность, % |
| `readiness` | float | 0..100 | готовность |
| `ammo` | float | 0..100 | боезапас, % |
| `fuel` | float | 0..100 | топливо, % |
| `equipment` | float | 0..100 | снаряжение, % |
| `fatigue` | float | 0..100 | усталость, % |
| `suppression` | float | 0..100 | подавление (расчётное, не задаётся вручную) |
| `order` | enum | см. §4.4 | приказ |
| `alive` | bool | — | элемент небоеспособен/уничтожен |

`VehicleGroup`: `vehicle_type`, `count_full`, `count_current`, `condition` (состояние техники, 0..100).

Потери в процентах не хранятся — вычисляются как `1 − current/full`.

### 4.2 Батальон (`Battalion`)

`id`, `name`, `side` (A/B), `elements: list[Element]`, `commander_influence` (0..100), `communications` (0..100 — общая связь, отдельно от `cohesion` элемента), `task` (задача боя), `state` (в бою / отступает / паника / разгромлен / задача выполнена).

Агрегаты (только для чтения, считаются на лету): суммарный л/с, суммарная техника, средневзвешенные мораль/опыт/снабжение, доля потерь, остаточная боеспособность.

### 4.3 Окружение (`Environment`)

- `terrain`: равнина / холмы / лес / застройка / болото
- `time_of_day`: день / ночь / сумерки
- `weather`: ясная / дождь / снег / туман
- `fortification_A`, `fortification_B`: 0..5
- `intel_A`, `intel_B`: нет / частичные / полные разведданные
- `max_turns`: предел длительности боя

### 4.4 Приказы

`атака`, `оборона`, `засада`, `разведка`, `закрепление`, `отступление`, `паническое бегство`.

Приказ задаётся на батальон, с возможностью переопределить у отдельного элемента. Для каждого приказа в конфиге — набор модификаторов: атака, защита, заметность, скорость обнаружения, расход боезапаса, прирост усталости, устойчивость морали, условие выполнения задачи.

`паническое бегство` — не только приказ ГМ, но и состояние, в которое элемент сваливается автоматически при провале проверки морали.

### 4.5 Опциональные параметры

У части параметров (в исходном описании ГМ они выделены курсивом) должна быть возможность отключения. В `config/toggles.yaml` — булев флаг на каждый: `fuel`, `equipment`, `vehicle_condition`, `readiness`, `commander_influence`, `intel`, `fatigue`. Выключенный параметр не участвует в формулах (модификатор = 1.0) и скрывается в интерфейсе.

Каталог `config/`, формат YAML, валидация через pydantic при загрузке — при ошибке приложение показывает понятное сообщение и не падает.

| Файл | Содержимое |
|---|---|
| `terrain.yaml` | модификаторы атаки, защиты, обнаружения, усталости, скорости для 5 типов местности |
| `weather.yaml` | модификаторы обнаружения, точности, усталости, техники |
| `time_of_day.yaml` | модификаторы обнаружения и точности |
| `orders.yaml` | матрица приказов (§4.4) |
| `element_types.yaml` | базовые характеристики типов элементов, приоритет как цели, уязвимость, противотанковый коэффициент |
| `experience.yaml` | множители для уровней 1–4 |
| `morale.yaml` | веса факторов изменения морали, пороги отступления/паники |
| `combat.yaml` | летальность, потолок потерь за ход, экспоненты формул, бонус первого удара |
| `supply.yaml` | расход боезапаса/топлива по приказам, штрафы при нехватке |

Требования: любая правка конфига применяется без перезапуска; в интерфейсе есть редактор с валидацией и кнопкой «сбросить к значениям по умолчанию»; эталонные дефолты лежат в `config/defaults/` и не перезаписываются.

## 6. Движок боя

### 6.1 Цикл

Бой идёт ходами до выполнения условия остановки: одна сторона разгромлена, отступила, выполнила задачу, либо достигнут `max_turns`. Каждый ход — строгая последовательность фаз, каждая фаза пишет в журнал.

1. **Восстановление** — спад подавления, восстановление усталости, подвоз снабжения от тылового элемента (если жив).
2. **Обнаружение** — для каждого элемента считается уровень контакта.
3. **Инициатива** — кто наносит удар первым.
4. **Выбор целей** — распределение огня.
5. **Воздействие** — расчёт нанесённого давления.
6. **Потери** — л/с и техника.
7. **Подавление**.
8. **Расход боезапаса и топлива**.
9. **Усталость**.
10. **Мораль**.
11. **Проверки конца хода** — отступление, паника, разгром, выполнение задачи.

### 6.2 Формулы (стартовые, все коэффициенты — из конфига)

Ниже — модель первой версии. Численные значения подлежат калибровке, структура — нет.

**Коэффициент состояния элемента:**
```
K_сост = k_опыт(experience)
       × k_мораль(morale)
       × k_связь(cohesion, communications)
       × (1 − suppression/100)
       × k_усталость(fatigue)
       × k_боезапас(ammo)
       × k_снаряжение(equipment)
```

**Огневая мощь элемента:**
```
Огонь = attack
      × (personnel_current / personnel_full)
      × K_сост
      × k_приказ_атк
      × k_местность_атк × k_погода × k_время
      × k_командир(commander_influence)
      × шум
```
где `шум` — случайный множитель из `combat.yaml` (например, 0.85…1.15).

**Устойчивость элемента:**
```
Защита = defense
       × (personnel_current / personnel_full)
       × K_сост
       × k_приказ_защ
       × k_местность_защ
       × k_укрепление(fortification)
```

**Потери за ход:**
```
Давление = Σ Огонь_атакующего_по_цели / (Σ Защита_цели + ε)
Доля_потерь = clamp(k_летальность × Давление ^ γ, 0, потолок_за_ход)
Потери_л/с  = personnel_current × Доля_потерь × (1 − укрытие_местности)
```

Потери техники считаются отдельным пулом: доля противотанкового воздействия атакующих элементов (из `element_types.yaml`) → потери `VehicleGroup`; часть выбитой техники уходит не в уничтожение, а в снижение `condition`.

**Распределение потерь внутри батальона** — пропорционально весам: доля элемента в целеуказании × уязвимость типа × (1 − укрытие).

**Обнаружение:**
```
Обнаружение = база_местность × k_погода × k_время × k_разведданные
            × k_скрытность_приказа_цели × k_опыт_наблюдателя
```
Результат → уровень контакта: `нет` / `частичный` / `полный`. Контакт задаёт, какая доля элементов противника доступна для выбора целей и с какой точностью. Не обнаруженный элемент не может быть целью.

**Инициатива:** `k_опыт + k_связь + k_приказ + k_разведданные + бросок`. Сторона с большим значением бьёт первой и получает бонус первого удара. Приказ «засада» даёт автоматический приоритет в первый ход контакта.

**Подавление:** `suppression += k_подавление × Давление`, в фазе восстановления спадает на `k_восстановление × (1 + k_опыт)`.

**Мораль:**
```
Δмораль = − k1 × доля_потерь_за_ход
        − k2 × прирост_подавления
        − k3 × доля_потерь_техники
        − k4 × (1 если элемент вне контакта со штабом)
        + k5 × commander_influence
        + k6 × k_опыт
        + k7 × (успех своей стороны в ходу)
```

### 6.3 Проверки конца хода

- `мораль < порог_отступления` → приказ элемента меняется на «отступление»;
- `мораль < порог_паники` → «паническое бегство»: дополнительные потери от преследования, брошенная техника, элемент выбывает из расчёта;
- `personnel_current / personnel_full < порог_разгрома` или все боевые элементы небоеспособны → батальон разгромлен;
- **выполнение задачи** — по приказу: *атака* — противник отступил или разгромлен; *оборона* и *закрепление* — выстоял N ходов; *засада* — нанёс ≥X% потерь и вышел из контакта; *разведка* — достиг заданного уровня разведданных; *отступление* — вышел из контакта, сохранив ≥Y% л/с.

## 7. Случайность и воспроизводимость

- У каждого боя один `master_seed` (целое число), отображается и задаётся вручную.
- Каждый бросок берётся из потока `Random(hash((master_seed, turn, phase, element_id)))`. Глобальный `random` не используется.
- Повторный прогон с тем же сидом, теми же подразделениями и конфигом даёт **побитово идентичный** результат, включая журнал.
- Сид сохраняется вместе с результатом; из отчёта можно запустить точный повтор.
- Обязательный тест: 50 прогонов одного сценария с одним сидом → одинаковый хеш журнала.

## 8. Журнал событий

Структурированный, не текстовый. Каждая запись:

```json
{
  "turn": 3,
  "phase": "casualties",
  "actor": "A/rota_1",
  "target": "B/rota_2",
  "event": "losses_inflicted",
  "before": {"personnel": 120, "morale": 64},
  "after":  {"personnel": 103, "morale": 51},
  "breakdown": [
    {"factor": "terrain:лес", "value": 0.75},
    {"factor": "order:атака", "value": 1.15},
    {"factor": "suppression", "value": 0.82},
    {"factor": "random", "value": 1.04}
  ],
  "text": "1-я рота потеряла 17 человек: огонь вёлся из леса, цель подавлена на 18%."
}
```

Поле `breakdown` обязательно для всех изменений потерь, морали и боеспособности — по нему ГМ видит, какие именно модификаторы сработали. В интерфейсе журнал фильтруется по ходу, элементу и типу события; экспортируется в Markdown и JSON.

## 9. Массовое моделирование

- Вход: сценарий + N прогонов (по умолчанию 100) + базовый сид.
- Прогон i использует сид `base_seed + i`.
- Выполнение в `multiprocessing.Pool`, в интерфейсе — прогресс-бар и отмена.
- Выход:
  - вероятность победы A / победы B / ничьей (лимит ходов);
  - средние, медианные и p10/p50/p90 потери каждой стороны (л/с и техника);
  - среднее число ходов, распределение по способам завершения (разгром / отступление / паника / задача / лимит);
  - гистограмма потерь и график распределения исходов;
  - таблица со всеми прогонами: сид, исход, потери — с возможностью открыть любой прогон покомпонентно.
- Экспорт сводки в CSV и Markdown.

## 10. Интерфейс (Flet)

Навигация — через `page.go()` / стек `View`, с рабочей кнопкой «назад», как в браузере. Переходы оформляются ссылками-кнопками.

| Маршрут | Экран |
|---|---|
| `/` | Главная: ссылки на разделы, последние бои и сценарии |
| `/units` | Список подразделений: создать, копировать, импорт/экспорт, удалить |
| `/units/{id}` | Конструктор: дерево элементов, добавление из шаблонов типов, правка всех полей, валидация, сводка по батальону |
| `/battle/setup` | Настройка боя: сторона A и B, окружение, укрепления, разведданные, приказы, задача, сид |
| `/battle/{id}` | Прогон: кнопки «шаг», «5 ходов», «до конца»; панели состояния обеих сторон (л/с, техника, мораль, подавление, снабжение, усталость); журнал текущего хода |
| `/battle/{id}/result` | Итог: текстовый вывод исхода + таблицы потерь, остаточной боеспособности, организации и снабжения; экспорт |
| `/batch` | Массовое моделирование: параметры, прогресс, статистика, графики |
| `/config` | Редактор коэффициентов по разделам, валидация, сброс к дефолту, тумблеры опциональных параметров |
| `/archive` | Сохранённые бои и сценарии, повтор по сиду |

Требования: тёмная и светлая тема; все числовые поля с ограничением диапазона и подсказкой; изменение параметра сразу отражается в сводке батальона; никакой расчёт не блокирует UI-поток дольше 100 мс — длинные операции в отдельном потоке.

## 11. Хранение

- Подразделения, сценарии, результаты — JSON в `data/`, схема версионируется полем `schema_version`.
- Конфиг — YAML в `config/`.
- Отчёт по бою экспортируется в Markdown и HTML, таблицы — в CSV.
- Файлы читаемые и правятся руками вне программы.

## 12. Качество

- Все модели — pydantic, полная типизация, `ruff check` без ошибок.
- Тесты `pytest`:
  - детерминизм по сиду (§7);
  - `core` не импортирует `flet`;
  - численность и техника не уходят в минус, потери не превышают наличие;
  - баланс: `потери + остаток == исходная численность` на каждом ходу;
  - каждый приказ, тип местности, погода и время суток участвуют хотя бы в одном тесте;
  - конфиг с ошибкой даёт понятное исключение, а не падение;
  - бой всегда завершается за ≤ `max_turns`;
  - равные батальоны в равных условиях на 200 прогонах дают вероятность победы 50% ± 5%.
- `cli.py`: `python cli.py --scenario data/scenarios/x.json --seed 42 --runs 100` — прогон без UI, вывод в консоль и файл. Нужен для быстрой калибровки.

## 13. Этапы

| Этап | Результат |
|---|---|
| M1 | Модели данных + загрузка/валидация конфига + storage + тесты |
| M2 | Движок: все фазы, формулы, проверки конца хода, RNG, журнал + тесты |
| M3 | `cli.py`: сценарий → результат в консоли. Точка калибровки чисел |
| M4 | UI: маршрутизация, список и конструктор подразделений, настройка боя |
| M5 | UI: прогон боя, журнал, итоговый отчёт, экспорт |
| M6 | Массовое моделирование со статистикой и графиками |
| M7 | Редактор конфигурации, тумблеры опциональных параметров, архив |

После каждого этапа — рабочее состояние и зелёные тесты. Не переходить дальше, пока предыдущий этап не запускается.

## 14. Критерии приёмки

1. Два батальона из 5–8 элементов проводят бой за ≤30 ходов; результат содержит потери в л/с и технике, остаточную боеспособность, организацию, снабжение и полный журнал.
2. Повтор по сиду даёт идентичный результат.
3. Любой коэффициент меняется из интерфейса и немедленно влияет на расчёт; правки кода не требуются.
4. 100 прогонов сценария выполняются и дают вероятности исходов, средние потери и диапазон.
5. Для любой строки потерь или изменения морали журнал показывает список сработавших модификаторов с числами.
6. Отключение любого опционального параметра не ломает расчёт.

## 15. Открытые вопросы к ГМ

Ответы нужны до этапа M3 (калибровка); до тех пор берутся значения по умолчанию.

1. Шкала `attack` / `defense`: абсолютная (условные единицы огня) или относительная (1.0 = типовая стрелковая рота)?
2. Сколько игрового времени занимает один ход — от этого зависят расход боезапаса, прирост усталости и `max_turns`.
3. Какие параметры из списка действительно опциональны — курсив не сохранился при переносе текста. Пока флаги в `toggles.yaml` стоят на: топливо, снаряжение, состояние техники, готовность.
4. «Влияние командира» — одно число на батальон или отдельный объект (командир с характеристиками, которого можно потерять вместе со штабом)?
5. Уровень связи — общий на батальон или у каждого элемента свой? Сейчас заложены оба; нужно понять, что из этого используется.
6. Нужен ли учёт нехватки топлива для пехотных элементов, или топливо касается только техники?
7. Задача боя задаётся ГМ вручную для каждой стороны или выводится из приказа?
